Qualifier · audit · 2026-09-12

The staff workspace, screen by screen

The security audit a day earlier closed the write side of the database. This one is about the other half: what the product actually lets a person do, and where it stops short of the job it claims to do.

4 blocker 14 high 25 medium 4 low

Scope: qualifier-web at 3b40927, all 7 pages, 4 API routes, 12 components and 9 lib modules, read in full; the profiles schema and user-management RPCs in qualifier-db at 66208c2; and the live site at qualifier-web.onrender.com, unauthenticated. No credentials were used and nothing was written. Identifiers are UX-n; where a finding is already owned by a ticket in docs/product-gap-analysis.md the margin says so.

If you fix five things

  1. Make the pipeline visible while it runs (UX‑7). Every mutation is followed by a refetch that executes before the background job it just queued could possibly have finished, under a notice that promises the opposite. The demo will expose this in the first three minutes.
  2. Let the underwriter open the document (UX‑10). Today they approve or decline having seen extracted fields and a confidence number, never the DUI itself.
  3. Build real user management (UX‑1). The screen is create-only. A departing employee's account cannot be revoked through the product at all — and set_staff_role(), with every guard and its audit row already written, has zero callers.
  4. Show the audit trail (UX‑20). Every decision is recorded server-side and no screen reads it. The regulatory selling point is invisible to the people who would be audited.
  5. Stop swallowing query errors (UX‑24, UX‑25). A failed documents query on the case screen renders as "no documents uploaded". There is no error boundary anywhere.

Where each screen stands

Graded on whether a real underwriting team could run a working day on it, not on code quality. Both detail screens are stronger than their list screens; the case queue — the screen the whole product funnels into — is the weakest thing in the app.

A. User management

The half you named. The database side was built properly in the 2026-09-11 migration and then never connected to a screen.

UX-1Blocker/registernew

User management is create-only, and there is no way to revoke an account

The nav item says Usuarios. The screen behind it lists four columns of plain text — name, role, company, date added — and each <tr> contains nothing else. There is no role change, no deactivate, no delete, no rename, no tenant move, no password reset, no resend invite. The only write on the page is "create".

The database is not the problem. set_staff_role() exists with every guard you would want: administrator-only, a role allowlist that excludes applicant, a rule that only a superadmin may grant or revoke superadmin, a tenant check for tenant_admin callers, and an audit_log row on success. It has zero callers in web. The five RPCs the app does call are assign_case, publish_playbook, submit_application, decide_case and request_case_info.

What this costs

An employee leaves. Their account keeps working. There is no is_active column to flip, no delete in the product, and demoting them — once that is even wired — still leaves them able to sign in and read the whole tenant's client portfolio, because every staff role can reach /clients. Removing them today means the Supabase dashboard.

Fix

Wire set_staff_role to a role select on each row, then add the column the schema is missing: profiles.is_active boolean not null default true, enforced in useStaffSession and — the part that matters — in RLS, so an inactive account cannot read rows even with a valid JWT. Deactivation belongs in a set_staff_active() function alongside its siblings, not in an UPDATE, for the same reason deciding a case does.

The screen admits it in its own copy: "Compártela por otro medio — todavía no hay correo de recuperación." Worth restating only because it shares its one missing piece — an email provider — with FUN-3, and because UX-1 is much less useful without it: you can add a user, but not help them when they lose the password you typed for them.

B. The pipeline is invisible while it runs

UX-7Blockerall screensnew

Nothing tells the UI the background work finished — and the copy says it will

There is no realtime subscription, no polling and no revalidation anywhere in the app: zero occurrences of channel(, postgres_changes, setInterval or router.refresh. Every mutation is followed by a single await load() that runs immediately — before the job it just enqueued could have started, let alone finished.

The notices promise otherwise, in Spanish, to the user's face:

application-detail.tsx:250  "Extracción reencolada. El estado se actualiza aquí en cuanto corra."
application-detail.tsx:257  await load();   ← the only refresh, and it is now

application-detail.tsx:269  "En unos segundos una nueva reemplaza la de abajo"
application-detail.tsx:275  await load();   ← same

applications/page.tsx:201   "la puntuación está corriendo y el caso aparecerá en Casos en breve"
applications/page.tsx:220   await load();   ← same

The user must reload by hand, and nothing on screen suggests it. On a free-tier Render worker with a cold start, the gap between the promise and the truth is around a minute.

What this costs

This is the demo-breaking one. The whole pitch is "upload documents, get back a scored case" — and the moment that happens is the moment the screen goes quiet and stays quiet. It also makes the case queue wrong for anyone who leaves it open: a case created by the pipeline never appears.

Fix

Supabase realtime on documents, scores and cases, filtered by the row you are looking at, is the direct answer and RLS already scopes it correctly. A poll with backoff while any document is pending or processing is the cheaper one and would carry the demo. Either way the copy should stop promising something the code does not do.

UX-8High/applications/[id]new

An underwriter cannot retry a failed extraction or rescore a case

Both buttons are gated on canUploadDocuments, which is tenant_admin and agent only. The exclusion is deliberate and correct for its stated reason — a superadmin has no tenant_id, so the storage policy's foldername[1] = current_tenant_id()::text comparison can never match — but the gate was reused for two actions that touch no storage at all, and it caught the underwriter on the way past.

So the person who owns the decision, looking at a case stuck on a failed extraction, has no button. They have to find an agent.

Evidence

web/src/lib/roles.ts:59-61              canUploadDocuments = tenant_admin | agent
web/src/components/applications/application-detail.tsx:489,569  rescore gated on canUpload
web/src/components/applications/application-detail.tsx:695      retry-extraction, same gate

Fix

Split the predicate. canUploadDocuments keeps its storage meaning; a new canReprocess covers retry and rescore and includes underwriter. Both routes already authorise by RLS probe rather than by role, so nothing downstream changes.

UX-9High—FUN-5

The dead-letter queue is invisible from the product

pg-boss retries five times with backoff and then drops the job in dead_letter. No screen reads it. A file that exhausts its retries leaves an application sitting in a state nobody is watching, and the only way to find out is /health/queue with a bearer token — an operator's tool, not a business one. Already owned by FUN-5; it belongs in the same piece of work as UX-7 and UX-8, since all three are "the pipeline talks back".

C. The document itself

UX-10Blocker/applications/[id], /cases/[id]new

Nobody can open the uploaded document

storage_path is written on upload and selected on read, and never rendered. There is no createSignedUrl and no getPublicUrl anywhere in src — no link, no thumbnail, no viewer, no download.

An underwriter therefore approves or declines a policy having seen the extracted fields, a per-field confidence percentage and an AI narrative, and never the DUI, the salary certificate or the medical report those were drawn from. When extraction is wrong — and the accuracy of extraction is, by the project's own gap analysis, the one thing that has never been measured — there is no way for a human to notice.

Evidence

application-detail.tsx:146   storage_path selected
application-detail.tsx:319   storage_path written
grep -rn "createSignedUrl\|getPublicUrl" web/src   0 matches

Fix

A short-lived signed URL minted server-side. Do it in a route rather than from the browser, because that is also the natural place to write the document.viewed row that SEC-2 asks for — the two are one piece of work, and doing the link from the browser now means doing it twice.

UX-11High/applications/[id]new

A document cannot be deleted, replaced, or given the right type

There is not a single .remove( or .delete() call in the codebase. Upload the payslip as dui and it is permanently a dui: the requirement indicator will go on reporting the real requirement unmet, the extractor will go on parsing it against the wrong schema, and the only remedy is to upload the same file again under the right type and leave the wrong row in place forever.

There is a related leak. If the storage upload succeeds and the documents insert then fails, the object stays in the bucket with no row pointing at it and no cleanup — the mirror image of the compensating deleteUser that api/users gets right.

UX-12Medium/applications/[id]new

Upload is one file at a time, with no progress, behind a flag that freezes the screen

e.target.files?.[0] — one file, no multi-select, no drag-and-drop. Progress is a single boolean, so there is no percentage and no per-file row; and because that boolean is shared, an upload in flight also disables every document's retry button and the rescore button. Registering an application with five required documents means five sequential uploads with the rest of the screen inert.

The validation around it is good and worth keeping: a 5 MiB cap and a five-type allowlist checked client-side before the request, re-enforced by the storage policy, with a deliberate exception for files whose type the browser reports as empty.

UX-19Medium/casesnew

SlaCell is carefully built — resolved cases never turn red, missing deadlines say "Sin fecha", under eight hours gets a warning badge — and it compares against a loadedAt captured once at fetch time, deliberately, to keep rendering pure. E. The audit trail is written and never read

UX-20Highall screensnew

Nothing in the product displays audit_log

The 2026-09-11 migration moved every staff transition into a security definer function that records what happened, revoked insert from authenticated, and left the table append-only with no update or delete policy for any role. It is a well-built audit trail. The only occurrence of the string audit_log in the entire frontend is a comment explaining that the function writes one.

So the case screen shows a decision but not who made it or when it changed hands; the client screen shows updated_at but not who edited it or what changed; and the compliance story — the reason a regulated buyer would choose this over a spreadsheet — cannot be demonstrated in the product at all. Note this is distinct from SEC-2, which is about writing document-access rows; this is about reading the rows that already exist.

G. Errors that never reach the person

UX-25Highapp shellnew

No error boundary, no not-found, no route-level loading

There is no error.tsx, global-error.tsx, not-found.tsx or loading.tsx anywhere in src/app. A throw in any client component — and every screen is a client component — takes the subtree down to Next's default. A bad URL gets the stock English 404, confirmed on the live site: "This page could not be found." in a Spanish product.

The detail goes to console.error and nowhere else: no telemetry, no server-side record that a user's enqueue failed.

H. There is no feedback system, only forty copies of one

UX-29Mediumapp-widenew

Every screen hand-rolls const [error, setError] and const [notice, setNotice] and renders its own paragraph, which is why the quality varies so much between them: role="alert" on five screens and missing on three, a dashed empty-state card here and a bare <p>Cargando…</p> there.

J. Responsive and theme

UX-35Mediumapp-widenew

The tablet range is unhandled by construction, and there is no mobile navigation

The codebase contains zero md: classes — only sm: and lg:, twenty-two occurrences across seven files. The sidebar is w-56 at every width with no collapse and no drawer, so on a phone a 224px rail sits permanently beside the content.

Three tables have no horizontal scroll container and will push the page sideways: /cases, /register and the case detail. The case detail's header uses flex justify-between with no flex-wrap. /clients, /applications and the client detail get this right, so the fix is a two-line copy from a neighbouring file.

Worth deciding rather than drifting: an underwriter reviewing a case on a tablet is a plausible use, an agent registering a client on a phone during a home visit even more so.

UX-36Lowapp shellnew

Dark mode is fully defined and completely unreachable

globals.css carries a complete .dark token set and the variant is wired. Nothing ever applies the class: no theme provider, no toggle, no prefers-color-scheme query, no stored preference. Three dark: utilities exist in the whole codebase, all in one badge component. Either finish it — a class on <html> and a toggle — or delete the tokens so the next person does not assume it works.

K. The playbook editor

The most sophisticated screen in the app by a distance — a fully structured form over every part of the schema, and a key-matched diff between versions that is real engineering, not a text compare. Its gaps are all on the safety side.

UX-37Highplaybook editornew

One validation runs before publish: that two numbers sum to 1

That is the entire client-side gate on a document that decides whether people get insured. Nothing checks for an empty rule id, a duplicate id, a malformed expression, a missing tier, tiers that do not cover the range, a disqualifier pointing at a rule someone deleted, or — the subtle one — an output_scale_adapter.map whose keys stop matching after a tier label is renamed in the field right above it.

"Rules are data, not code" is the product's founding invariant, and the price of it is that the validator has to be the product's job. Today the only real validation lives in the grading engine, reached through an optional test button, and its output is a JSON blob.

Evidence

playbook-editor.tsx:386        weightSum !== 1  ← the whole gate
playbook-editor.tsx:1085       disabled={weightSum !== 1}
playbook-editor.tsx:1035       renaming a tier label orphans its map entry
package.json                   no zod, no expr-eval — nothing parses an expression

Fix

A shared schema module both web and grading-engine import, so the editor validates against the same definition the engine enforces rather than a hand-copied TypeScript interface. Short of that, a publish-time call to the existing /score route with a synthetic sample, blocking publication on a validation error.

UX-38Mediumplaybook editornew

No rollback, and a new draft can only be cloned from the newest version

handleNewDraft always clones playbooks[0]. If v4 turns out to be wrong, there is no "restore v3" and no "start a draft from v3" — you clone v4 and retype the differences by hand, reading them off the diff panel that sits right there and knows exactly what they are.

Published versions are immutable by database trigger, which is correct and is precisely why a first-class rollback is needed: the safe path is to publish a new version identical to an old one, and the editor gives no way to produce it.

UX-39Mediumplaybook editornew

The test panel shows a tenant admin the engine's internals

A successful run is the whole upstream body JSON.stringify'd into a <pre>; a failure is the grading engine's raw validation object, pretty-printed. And when the upstream returns something that is not JSON, the body becomes null and the panel renders the four characters null.

The person this screen is built for is an insurer's business analyst — the entire product thesis is that they can edit rules without an engineer. The response has final_score, decision and rule_trace in it; rendering those three is most of the work.

UX-40Mediumplaybook editornew

You cannot walk from a playbook version to the decisions it produced

"Every decision records the exact playbook version that produced it" is a stated invariant, and the link is stored — the application row carries playbook_id and playbook_version, and the detail screen displays v4 as plain text. It is not a link, and there is no traversal the other way: the version list cannot tell you that v3 scored 40 applications and v4 has scored two.

That count is what makes publishing a new version feel safe, and it is also the answer to the question a regulator asks first.

UX-41Lowplaybook editornew

Publish goes straight from the browser behind a native confirm()

supabase.rpc("publish_playbook") called from the client, guarded by window.confirm, surfacing rpcError.message — a raw PostgREST string — into the page. The RPC itself is transactional and the trigger is the real safety net, so this is a polish item, not a hole. But it is the app's only confirmation dialog and it protects the wrong action relative to UX-13.

UX-43HighrepoCAL-3

Zero tests, and every fix above lands without one

No runner, no config, no test script, no test step in CI — the workflow runs typecheck, lint and build. Restated here only for its interaction with this report: forty-seven changes are about to go into the repo with the most churn and all of the business logic, and the strongest check available is that it compiles.

The cheapest useful first suite is not component tests. It is Playwright driving the seven accounts in the next section through sign-in, one role gate, and one decision.

UX-44Mediumapp shellnew

No middleware, so no session is ever refreshed

There is no middleware.ts, and the server client's setAll() is a deliberate no-op because route handlers cannot reliably write cookies. Between them, nothing in the app ever writes a refreshed session cookie. A staff user whose access token expires mid-session is bounced to /forbidden rather than transparently renewed.

The security posture is fine — RLS is the boundary and roles.ts says so in its first nine lines — but the experience is not: an unauthenticated visit to /cases renders the app shell and "Verificando tu sesión…" before redirecting, which is both a flash of chrome and a slower path than a server redirect.

UX-45Mediumapp shellnew

The session is read once per mount and never watched

useStaffSession runs one effect with no onAuthStateChange subscription, no refetch on focus and no polling. Sign out in one tab and the other keeps rendering the dashboard until something navigates. More pointedly: once UX-1 lands, a role change will not take effect until the affected user reloads — including a demotion.

UX-46Low4 API routesnew

No timeout on any outbound call, on a platform where cold starts take a minute

No AbortSignal, no maxDuration, no route segment config anywhere. On paid infrastructure this is a footnote. On Render's free tier, where a service that has been idle fifteen minutes takes about a minute to answer, it means a spinner with no ceiling and no explanation — and the retry helper's three attempts with 500 ms backoff all expire long before the worker wakes.

UX-47Low4 API routesnew

Two small inconsistencies across the four routes

The missing-environment-variable 500 is returned before the auth check in all four, so an unauthenticated caller can learn which backends are configured — minor, but free to fix by moving three lines. And user.is_anonymous is checked in api/users and api/playbooks/test and not in process or extract; those two are still gated by an RLS probe, so it is a consistency gap rather than a hole.

The test accounts

Second half of the brief: sign-in accounts that identify Claude's activity in the data. Seven of them, one per role and tenant, which also closes BLK-7 — the ticket for the three roles nobody has ever signed in as.

On the address

claude.test, not claude.com. The identifier is what you asked for and it survives; the domain does not resolve, ever, because .test is reserved by RFC 2606 for exactly this. That matters here specifically: BLK-6 and FUN-3 both add outbound email, and on the day SMTP is configured every one of these addresses becomes a live send to a domain the project does not control — including Supabase's own recovery flow, which anyone who knows the address can trigger. The existing create-test-accounts.mjs already chose .test for this reason and says so at line 39. And there is no delete path in the product, so the choice is sticky.

How to build it

Extend web/scripts/create-test-accounts.mjs rather than writing a second script. It already has the parts that are annoying to get right: a hidden password prompt that refuses to run without a TTY, an idempotent skip that looks accounts up rather than trusting createUser's error text, a profile upsert, and an explicit warning for the auth-user-without-profile state. Four changes:

  1. Replace the three-entry ACCOUNTS array with these seven, keeping the why field — it is the reason the file reads well.
  2. Set a real full_name per account rather than falling back to the address — "Claude · Analista (Seguros)" and so on. This is what actually delivers the identification you asked for: it is the string that shows up in the assignee dropdown, in the case row, and beside a comment once UX-15 is fixed.
  3. Offer one password for all seven, prompted once. Seven hidden prompts is the kind of friction that gets a script abandoned halfway.
  4. Fix two stale references while you are in the file: it points at session-notes.md, which does not exist in this workspace, and tells you to sign in at /login, which redirects to /.

Before running it

web/.env.local does not exist — the script needs NEXT_PUBLIC_SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY from qualifier-secrets.env.txt, and .env.local is gitignored. There is one Supabase project and it is production, so these accounts are being created in production; that is unavoidable until BLK-4 and it is the same situation the existing script has always been in.

Two consequences worth knowing before, not after. Re-running db/supabase/seed.sql assigns cases by subquery to whoever holds the underwriter account — which will now be Claude's — and it deletes every row in both tenants, including any real pipeline run from BLK-5. And deleting a tenant cascades to its staff profiles, which would leave these auth users orphaned into permanent /forbidden accounts that the product has no way to remove.

What to do with them once they exist

They are the missing half of PLAN.md step 1 and they make it a real matrix rather than a walkthrough: sign in as each, confirm the nav is right for the role, confirm agent-medico cannot see a seguros client, run one application through the pipeline as an agent, decide it as the underwriter, and check audit_log gained the row. Then keep them: they are also the fixtures the Playwright suite in UX-43 should drive.

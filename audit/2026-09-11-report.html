Findings

Ranked by what an attacker, or an ordinary mistake, could do. Each finding names how it was verified. None was attempted against production. The twelve probes ran against the repo's own migrations in a local Postgres 17 replay. Production's policies were read from its catalog and match the repo's.

CriticalC1

Any tenant admin can make themselves superadmin

profiles_admin_write lets a tenant admin update any profile in their tenant, their own included, and nothing protects the role column. The policy's check calls app_current_role(), a STABLE function that still sees the pre-update row. So it approves the promotion it should refuse. Once promoted, the admin reads and writes every tenant.

No UI is needed. The admin's own session plus the public anon key reach PostgREST directly. The rule in /api/users ("only a superadmin can mint another") exists only in the route, never in the database.

Evidence

# P1 attempt: no error
not ok 1 - P1 a tenant_admin cannot promote themselves to superadmin
#   have: superadmin
#   want: tenant_admin
not ok 2 - P2 tenant A's admin still cannot read tenant B's applications
#   have: 1
#   want: 0

Fix

In one migration: revoke update (role, tenant_id) on profiles from authenticated, and route role changes through an RPC that checks the caller explicitly. Add a check constraint that a superadmin has no tenant. Then add P1 and P2 to the pgTAP suite so this stays fixed.

HighH1

Underwriters can write scores, including into another tenant

scores_system_write checks only the caller's role, never the tenant. Scores are the pipeline's output, and the pipeline writes with the service role, which bypasses RLS. So no signed-in role needs to insert them at all. As things stand, an underwriter can put a hand-made "approve" on their own tenant's application. Given the other tenant's application ID, they can write one onto that tenant's too. "Every decision records the exact playbook version that produced it" is only as true as this table.

Evidence

not ok 3 - P3 an underwriter in tenant A cannot write a score into tenant B
not ok 4 - P4 an underwriter cannot write the pipeline's score for their own tenant's application

Fix

Drop the policy, and revoke insert, update on scores from authenticated. Nothing in web writes scores, so nothing breaks.

HighH2

Who decides a case is enforced in React, not in the database

The applications and cases policies check tenant membership only. An agent, the intake role, can approve an application and resolve a case directly. roles.ts says every UI gate mirrors a policy. For decisions, none exists. The decision itself is two to four separate browser writes (case-detail.tsx:141–165), so a failure between them leaves the application approved and the case open.

Evidence

not ok 5 - P5 an agent (intake role) cannot approve an application
not ok 6 - P6 an agent cannot resolve a case

Fix

A decide_case() RPC, built the way publish_playbook() already is. It checks the role, updates the application and the case, and writes the comment and the audit row in one transaction. Then narrow the table policies so status changes can only happen through it. This one change also fixes H3.

HighH3

No decision has ever reached the audit log

The case screen writes its audit entries (approve, decline, request information, assign) and its comments without tenant_id. The column has no default, so RLS rejects every one. The screen never checks those errors, and it shows the decision as saved. Production confirms this: the only audit rows are the 11 seeded system application.scored entries. A comment typed alongside a decision is also lost without notice.

Evidence

# P10 attempt: new row violates row-level security policy for table "audit_log"
not ok 10 - P10 the case screen's decision audit insert is recorded
# P11 attempt: new row violates row-level security policy for table "case_comments"
not ok 11 - P11 the case screen's comment insert is recorded

Fix

Folded into decide_case() (H2). The assignment write in cases/page.tsx:210 needs the same treatment. Until then, passing tenant_id and surfacing the error would at least make the loss visible.

MediumM1

The playbook test endpoint answers anyone

POST /api/playbooks/test has no session check. It forwards whatever it receives to the grading engine with the service token attached. So anyone on the internet can run scoring on the free-tier engine, through the very boundary the token exists to guard. It exposes no tenant data.

Evidence

$ curl -X POST -d '{}' https://qualifier-web.onrender.com/api/playbooks/test
{"error":{"formErrors":[],"fieldErrors":{"playbook":["Required"],"fields":["Required"]}}} [400]   # the engine's own validator answered
$ curl -X POST https://qualifier-web.onrender.com/api/users
{"error":"unauthenticated"} [401]   # what it should look like

Fix

Require a signed-in tenant admin or superadmin, as /api/users does, and cap the body size.

MediumM2

The pipeline follows cross-tenant pointers the browser wrote

Foreign keys don't carry the tenant. So an application can name another tenant's playbook, and a document can attach itself to another tenant's application. The orchestrator then reads both with the service role and no tenant check. It will score with the other tenant's rules and copy their rule trace into this tenant's score, and it will feed a foreign document into the other tenant's case. It also downloads whatever storage_path a document row names. RLS hides the IDs this needs, so this is missing defence in depth rather than an open door.

Evidence

not ok 8 - P8 an application cannot point at another tenant's playbook
not ok 9 - P9 a document cannot be attached to another tenant's application

Fix

Composite foreign keys on (tenant_id, id). In processApplication and extractDocument, assert that the playbook's tenant matches, and that storage_path starts with {tenant_id}/{application_id}/.

MediumM5

Re-running an application duplicates its score, its case and its model spend

processApplication makes both Claude calls, then writes the score, the status, the case and the audit rows as separate statements. Nothing is unique per application: production has only primary keys on scores and cases. A failure at the case insert gets retried, and pg-boss allows five retries. That can mean up to six score rows and twelve paid model calls for one application. A successful run that is triggered again opens a second case.

Fix

A unique index on open cases per application. Skip the model calls when a score already exists for that application and playbook version. Do the writes in one RPC transaction.

What held up

  • Tenant read isolationAll 31 RLS assertions pass under pg_prove semantics. Every table has RLS on and a policy.
  • The rules engine fails closedA rule that can't be evaluated leaves a sentinel row and forces manual review. The tests cover exactly that path.
  • Service-to-service authDigest compare in constant time, a 32-character minimum, and no boot without a token. The routes that should answer 401 do.
  • Document storagePrivate bucket, 5 MB cap, MIME allowlist. MIME is sniffed from the bytes, not the filename.
  • Queue designStately singleton dedupe, a dead letter that closes out stuck documents, and a health check that reads job age, not depth.
  • Database hygieneViews run as security_invoker, definer helpers pin search_path, and every container runs as a non-root user.

Method and limits

Live checks: health, queue and token probes against all three Render services, plus unauthenticated requests to every web API route. The production database was read inside a read only transaction for its policies, grants, constraints, functions, buckets and row counts. No write was attempted there.

The CI workflow was replayed step by step against PGlite (Postgres 17) with a pgTAP stand-in for the seven functions the suites use. The twelve probes ran in that same database after the replay's migrations and seed. They are saved next to this report as audit/2026-09-11-probes.sql in the umbrella repo, ready to move into db's suite as each fix lands.

Not covered: a signed-in pass through the UI, GitHub Actions results, a line-by-line review of the large React components, and prompt-injection resistance of the three agents against hostile document content. That last one deserves its own look before real applicants' files arrive.

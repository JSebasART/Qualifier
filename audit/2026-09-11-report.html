CriticalC1Fixed

Any tenant admin could make themselves superadmin

profiles_admin_write let a tenant admin update any profile in their tenant, their own included, and nothing protected the role column. The policy's check calls app_current_role(), a STABLE function that still sees the pre-update row — so it approved the promotion it should have refused. Once promoted, the admin read and wrote every tenant. No UI was needed: the admin's own session plus the public anon key reach PostgREST directly.

Evidence

# P1 attempt: no error
not ok 1 - P1 a tenant_admin cannot promote themselves to superadmin
#   have: superadmin
#   want: tenant_admin

What changed

Column privileges, because RLS decides rows and cannot decide columns: update on profiles is revoked from authenticated, and only full_name is granted back. Role changes go through set_staff_role(), which refuses to grant or revoke superadmin unless the caller already is one, refuses to touch another tenant, and writes its own audit row. A check constraint keeps a superadmin out of every tenant.

HighH1Fixed

Underwriters could write scores, including into another tenant

scores_system_write checked only the caller's role, never the tenant. An underwriter could put a hand-made "approve" on their own tenant's application, and — given the other tenant's application id — onto theirs. "Every decision records the exact playbook version that produced it" was only as true as this table.

Evidence

not ok 3 - P3 an underwriter in tenant A cannot write a score into tenant B
not ok 4 - P4 an underwriter cannot write the pipeline's score for their own tenant's application

What changed

The policy is dropped and insert, update, delete on scores revoked from authenticated. Scores are written by the pipeline's service role, which bypasses RLS, so no signed-in role needed this at all. Nothing in web wrote scores.

HighH2Fixed

Who decides a case was enforced in React, not in the database

The applications and cases policies checked tenant membership only, so an agent — the intake role — could approve an application and resolve a case directly. roles.ts said every UI gate mirrored a policy; for decisions, none existed. The decision itself was two to four separate browser writes, so a failure between them left an approved application on an open case.

Evidence

not ok 5 - P5 an agent (intake role) cannot approve an application
not ok 6 - P6 an agent cannot resolve a case

What changed

Status became a transition rather than a field. decide_case(), request_case_info(), assign_case() and submit_application() check the caller's role and tenant, move the application and the case together, and write the audit row in the same transaction. Direct writes to those tables are revoked, and the case screen calls the functions. An agent no longer sees decision buttons, because the function would refuse them.

HighH3Fixed

No decision had ever reached the audit log

The case screen wrote its audit entries (approve, decline, request information, assign) and its comments without tenant_id. The column has no default, RLS rejected every one, and the screen never checked those errors — it showed the decision as saved. Production confirmed it: the only audit rows were the 11 seeded system application.scored entries. A note typed alongside a decision was lost the same way.

MediumM2Fixed

The pipeline followed cross-tenant pointers the browser wrote

Foreign keys didn't carry the tenant, so an application could name another tenant's playbook and a document could attach itself to another tenant's application. The orchestrator then read both with the service role and no tenant check: it would score with the other tenant's rules and copy their rule trace into this tenant's score, and it would download whatever storage_path a row named.

Evidence

not ok 8 - P8 an application cannot point at another tenant's playbook
not ok 9 - P9 a document cannot be attached to another tenant's application

What changed

Composite foreign keys on (tenant_id, id) make "same tenant" a property of the schema; production satisfied them already. The orchestrator also checks at read time, because a confused-deputy read is worth refusing twice: it asserts the playbook's tenant, and that a document's path sits inside its own {tenant}/{application}/ folder. A row that fails the path check is rejected, not retried — it should never have existed.

MediumM5Fixed

Re-running an application duplicated its score, its case and its model spend

processApplication made both Claude calls, then wrote the score, the status, the case and the audit rows as separate statements. Nothing was unique per application. A failure at the case insert was retried, up to five times: as many as six score rows and twelve paid model calls for one application.

What changed

Processing resumes instead of repeating. If a real score already exists for this playbook version, the orchestrator does what is left — status, case, the audit row for a case it actually opened — without re-running the agents. A blocked score (missing documents, no tier) deliberately doesn't count, because re-running those is what the retry control is for. A partial unique index makes a second open case impossible, and a lost race is treated as success.

MediumM6Fixed

Four of five repos tested only what was already being deployed

CI ran on pushes to main and on PRs. Work lands on develop and reaches main by fast-forward, which deploys — so CI first saw a change on its way to production. Nobody here could read Actions results either (private repos, no gh), which is how db stayed red for six weeks.

What changed

develop added to every trigger. db's workflow also had to stop granting table privileges after the migrations ran: that would have re-granted exactly what the new migration revokes, and the write suite would have passed against privileges production does not have. It now mirrors Supabase's default privileges before any table exists.

What held up

  • Tenant read isolationAll 31 RLS assertions pass. Every table has RLS on and a policy — the read side was right all along.
  • The rules engine fails closedA rule that can't be evaluated leaves a sentinel row and forces manual review. The tests cover exactly that path.
  • Service-to-service authDigest compare in constant time, a 32-character minimum, and no boot without a token.
  • Document storagePrivate bucket, 5 MB cap, MIME allowlist, and the type sniffed from the bytes rather than the filename.
  • Queue designStately singleton dedupe, a dead letter that closes out stuck documents, and a health check that reads job age, not depth.
  • Database hygieneViews run as security_invoker, definer helpers pin search_path, and every container runs as a non-root user.

Method and limits

Live checks: health, queue and token probes against all three Render services, plus unauthenticated requests to every web API route. The production database was read inside a read only transaction for its policies, grants, constraints, functions, buckets and row counts. No write was attempted there, before or after the fix.

The CI workflow was replayed step by step against PGlite (Postgres 17) with a pgTAP stand-in for the seven functions the suites use — which is also how the pre-fix state was established: the replay reproduced the exact failure that had been turning db's CI red since 2026-07-31. The twelve probes are audit/2026-09-11-probes.sql; their durable form is now db's write_authorization_test.sql, 38 assertions that run on every push.

Not covered: a signed-in pass through the UI, GitHub Actions results, a line-by-line review of the large React components, and the agents' resistance to hostile document content.
